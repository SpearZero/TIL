## 서론

### 1.1 소프트웨어 아키텍처의 정의
- **아키텍처 스타일**
- 아키텍처가 반드시 지원해야 할 **아키텍처 특성**
    - 주요 성질과 성공 기준을 정의한다. (~성, 가용성, 신축성 등등)
    - 시스템이 무엇을 해야하는지를 결정한다.
- 시스템의 행동 방식을 구현하는 **논리적 컴포넌트**
    - 시스템의 행동방식을 규정한다.
- **아키텍처적 결정**
    - 시스템 구성 방식에 대한 규칙들을 정의한다.
    - 시스템에 제약조건을 추가하며, 개발 팀이 무엇을 해도 되는지, 안되는지에 대한 지침을 제공한다.

아키텍처 특성과 논리적 컴포넌트를 분석해 **적절한 아키텍처 스타일을 결정하고 구현한다.**

### 1.2 소프트웨어 아키텍처의 법칙

제1법칙
```
소프트웨어 아키텍처의 모든 것은 트레이드오프이다.
```

제2법칙
```
어떻게(방법)보다 왜(이유)가 더 중요하다.
```

### 1.3 아키텍트의 기대 역할
- 아키텍처적 결정을 내린다.
    - 기술 선택의 지침이 될 무언가를 제시
    - 특별한 경우를 제외하고 기술 결정 사항을 직접적으로 명시하지 않음
- 아키텍처를 지속적으로 분석한다.
    - 지속적으로 분석하고 개선 방안을 제안한다.
- 최신 트렌드를 계속 따라간다.
    - 트렌드를 궤뚫고 있어여 미래에도 유효한 결정을 내릴 수 있다.
- 결정 사항의 준수를 보장한다.
    - 아키텍처적 결정과 설계 원칙을 개발 팀들이 실제로 따르는지 지속적으로 확인한다.
- 다양한 기술을 이해한다.
    - 모든 부분에 전문가일 필요는 없지만 다양한 기술에 어느정도 익숙해야 한다.
- 비즈니스 도메인을 숙지한다.
    - 비즈니스의 요구사항들을 이해하지 않은 채로 효과적인 아키텍처를 설계하기는 어렵다.
- 대인 관계 스킬을 갖춘다.
    - 아키텍처는 기술 지침 제공뿐만 아니라 개발 팀을 이끌어 아키텍처를 실제로 구현하도록 주도하는 일까지 포함한다.
- 정치를 파악하고 헤쳐 나간다.
    - 조직 내 정치적 상황을 잘 파악하고, 협상 능력을 발휘해 대부분의 결정을 승인받아야 한다.
