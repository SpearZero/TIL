## 아키텍처적 사고
아키텍처적 사고는 사물을 설계자의 눈으로 보는 것, 즉 아키텍처의 관점에서 바라보는것이다.

### 아키텍처와 설계의 차이
- 소프트웨어 아키텍처는 시스템의 겉모양보다 **구조**에 초점을 둔다.
    - MSA 선택 등
- 사용자 인터페이스 화면의 느낌과 모양은 시스템의 **설계**를 정의한다.

아키텍처와 설계의 판단 조건
- 전략적 vs 전술적
    - 아키텍처는 전략적, 설계는 전술적
- 변경이나 구조에 얼마나 많은 노력이 필요한가
    - 많은 노력은 아키텍처 적은 노력은 설계
- 트레이드 오프가 얼마나 중요한가.
    - 중요한 트레이드오프는 아키텍처, 덜 중요한 트레이드오프는 설계

#### 전략적 결정과 전술적 결정
보통 전략적인 결정은 장기적이고 전술적 결정은 단기적이다.
- 전략적인 결정이 더 많은 사고와 계획이 필요하다.
- 전략적 결정은 다수의 사람이 관여한다.
- 장기적일 경우 전략적 아키텍처이다.

#### 노력의 정도
변경에 많은 노력이 필요하다면 아키텍처에 가깝고, 노력이 거의 들지 않으면 설계쪽에 가깝다.
- 모놀리스를 마이크로 서비스로 이전하려면 많은 노력이 필요하다. 따라서 아키텍처에 가깝다.

#### 트레이드오프의 중요성
결정에 대한 트레이드오프를 분석하면 그것이 아키텍처와 설계 중 어느쪽에 더 연관된 결정인지 판단하는데 도움이된다.
- 트레이드 오프가 클수록 아키텍처에 가깝다. 작을수록 설계쪽에 가깝다.
- MSA vs 클래스 파일 쪼개기

### 기술적 너비
- 개발자는 제몫을 다하려면 기술적 깊이가 깊어야한다.
- 소프트웨어 아키텍트는 기술적 너비가 더 중요하다.

지식 피라미드
- 알고 있는 것
    - 기술전문가가 일상 업무에 사용 하는 기술(언어, 프레임 워크 등)
- 모른다는 것을 아는 것
    - 들어는 봤지만 실제 경험이나 전문성이 없는 것
- 모르는 줄도 모르는 것
    - 가장 큰 부분을 차지한다.
    - 주어진 문제의 해법이 될 수 있는 각종 기술, 도구, 프레임워크, 언어가 모두 포함된다.

한 개인의 경력에서 목표는 **모르는줄도 모르는 것**에 속하는 지식을 **모른다는 것을 아는 것**의 영역으로 옮기고, 전문성이 요구되는 상항이 되면 **알고 있는 것**으로 승격하는 것이다.

- 개발자는 **알고있는 것(기술적 깊이)** 에 집중하게 된다.
- 아키텍트가 되기 위해서는 알고있는 것과 **모른다는 것을 아는 것(기술적 너비)** 가 중요하다.
    - 아키텍트에게는 너비가 깊이보다 중요하다.
    - 많은 영역의 전문성(깊이)을 유지하려다 어느 하나도 성공하지 못한다.
    - 오래된 지식을 앞선 정보라고 착각하면 안된다.

#### 20분 규칙
기술적 너비를 채우기 위해서 하루에 최소 20분을 새로운 내용을 학습하거나 특정 주제에 대해 더 깊이 파고드는데 사용한다.
- 아티클을 읽거나 유행어나 용어를 검색한다.
- 여러 지식이 '모르는 줄도 모르는 것' → '모른다는 것을 아는 것'의 영역으로 이동한다.

#### 개인 레이더 개발
기술의 진보를 무시하면 안된다.
- 그동안 열심히 연마했던 기술들이 거품처럼 사라질 수 있다.

기술레이더는, 각 기술에 대해 좀 더 체계적으로 생각하고, 상반되는 여러 결정 기준을 균형 있게 조율하는 데 도움이 된다.

### 트레이드오프 분석
아키텍트처럼 사고한다는 것
- 모든 해법에서 트레이드오프를 찾아내고, 그 장단점을 분석해서 최선의 해법을 도출하는것

아키텍처에 대한 정답
- 상황에 따라 다르다.
- 배포 환경, 비즈니스 목표, 조직 문화, 예산, 일정, 개발자의 역량같은 수많은 요소에 따라 달라짐

경매 시스템 예시
- Bid Producer가 입찰 생성
- Bid Capture, Tracking, Analytics 등에 전달
- 비동기 방식
  - 대기열(Point-to-Point)
  - 토픽(Publish-Subscribe)

토픽(Publish-Subscribe)
- Producer는 하나의 토픽에만 발행
- 여러 서비스가 동일 토픽을 구독
- 새 서비스 추가 시 토픽 구독만 추가
- 결합도가 낮고 확장성이 좋음
- 단점
    - 데이터 접근 제어가 어려울 수 있음
    - 모든 소비자가 동일한 메시지 계약을 공유
    - 소비자별 메시지 적체량 모니터링 / 오토스케일링이 어려움

대기열(Queue)
- 서비스마다 별도 대기열 필요
- 새 서비스 추가 시 Producer에도 연결 로직 추가
- 토픽보다 결합도와 변경 비용이 높음
- 장점
    - 특정 소비자에게만 메시지 전달 가능
    - 소비자마다 독립적인 메시지 계약 사용 가능
    - 큐별 적체량 모니터링 가능
    - 소비자별 부하 분산 / 오토스케일링 가능

정리
- **토픽:** 낮은 결합도, 높은 확장성
- **대기열:** 높은 제어력, 소비자별 독립성 및 모니터링

이와같이, 모든 것에 장점과 단점이 존재한다. 따라서 트레이드오프들을 꼼꼼히 따져봐야한다.

### 비즈니스 동인의 이해
아키텍트처럼 생각하기 위해서는 시스템 자체를 이해하는 것을 넘어서 시스템의 성공에 필요한 비즈니스 동인(driver)들도 이해하고, 이를 확장성, 성능, 가용성 같은 아키텍처 특성들로 옮길 수 있어야 한다.
- 비즈니스 도메인에 대한 이해와 비즈니스 이해관계자들과 협력적인 관계를 맺어야 한다.

### 아키텍처와 코딩 실무의 균형
아키텍트는 병목 함정에 빠지지 말아야 한다.
- 아키텍트가 시스템의 핵심 경로에 위치한 코드를 소유하고, 그 결과 팀 전체의 병목이 되면 안된다.

병목을 피하는 방법
- 시스템의 핵심 부분을 개발 팀 내 다른 이들에게 위임한다.
- 아키텍트는 향후 필요한 소규모 비즈니스에 초점을 둔 코딩 실무를 맡는다.
- 긍정적인 효과
    - 아키텍트가 코드를 작성하며 팀의 병목이 되지 않는다.
    - 개발자들이 시스템에 더 깊이 이해하게 만들 수 있다.
    - 아키텍트가 개발 팀과 동일한 비즈니스 관련 소스 코드를 작성하게 된다. 
        - 아키텍트가 팀이 겪는 고충을 더 잘 이해하게 된다.

아키텍트가 개발 팀과 함꼐 코드를 작성할 수 없는 경우의 실무감각 유지 및 기술적 깊이를 보장하는 방법
- PoC를 자주 진행한다.
    - 직접 코드를 작성하게 되며, 아키텍처적 결정을 실제 구현 관점에서 검증하는데 도움이 된다.
- 기술 부채 해결
    - 기술부채가 해결되면 개발 팀은 중요한 기능적 사용자 스토리 작업에 집중 가능하다.
    - 기술 부채는 대부분 우선순위가 낮으므로 작업을 완료하지 못해도 회사에 치명적이지 않다.
- 버그 잡기
    - 실무 감각을 유지하며 개발 팀에 도움을 줄 수 있다.
- 자동화
    - 개발팀에 도움이 될 수 있다.
- 코드 검토
    - 코드를 작성하지 않더라도 코드에 관여하며, 아키텍처 준수 여부 점검이 가능하다.
