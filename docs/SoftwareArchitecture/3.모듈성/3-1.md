## 모듈성

'지속 가능한' 코드베이스를 위해서는 좋은 모듈성이 제공하는 질서와 일관성이 꼭 필요하다.

### 3.1 모듈성 대 세분도
- 모듈성
    - 시스템을 더 작은 조각으로 나누는 것에 관한 것
- 세분도
    - 모놀리스에서 마이크로서비스 같은 고도로 분산된 아키텍처 스타일로 이동하려면 시스템을 잘게 쪼개야 한다.
    - 세분도는 시스템의 작은 조각들의 크기에 관한 것이다.

세분도는 서비스나 컴포넌트가 서로 결합하게 만드는 요인으로 작용한다.
- 서비스 및 컴포넌트 간의 전반적인 결합 수준에 항상 주의를 기울여야 한다.

### 3.2 모듈성의 정의
모듈성
- 서로 연관된 코드를 논리적으로 묶는 활동을 설명하는 데 사용
    - 이 책에서는 연관된 코드 묶음(클래스, 함수 등)을 통칭하는 일반적인 용어로 사용
- 객체 지향 언어의 클래스 그룹, 구조적 언어나 함수형 언어에서 함수 그룹 등은 논리적 그룹

아키텍트는 개발자들이 코드를 어떤 식으로 패키징하는지 알아야 한다.
- 패키징이 아키텍처에 중요한 영향을 미친다.
- 다수의 패키지가 긴밀하게 결합되어 있으면, 관련 작업을 위해 그중 하나를 재사용하기가 더 어려워진다.

### 3.3 모듈성의 측정

모듈성 측정을 위한 세 가지 지표
- 응집
- 결합
- 동변성

#### 3.3.1 응집
하나의 모듈을 구성하는 요소들이 정말로 그 모듈 안에 들어 있어야 하는가에 관한 것

모듈을 구성하는 요소들이 서로 얼마나 관련이 있는지를 측정하는 지표

```
응집력 있는 모듈을 나누려 해 봤자 결합도가 증가하고 가독성이 떨어질 뿐이다.
- 래리 콘스탄틴
```

응집의 유형 (최선에서 최악순)
- 기능적 응집, 순차적 응집, 통신적 응집, 절차적 응집, 시간적 응집, 논리적 응집,우발적 응집

특정 모듈의 응집도는 특정 아키텍트의 재량에 따라 결정되는 경우가 많다.

고객 관리 예시
- 고객 관리 모듈에 고객 추가/갱신/조회/알림 항목과 주문 조회, 주문 취소가 있는 경우
- 주문 관련 항목은 고객 관리 모듈에 필요하지 않을 수 있다.
- 고객 관리 모듈을 고객 관리, 주문 관리로 나눌 수 있음

고객 관리, 주문 관리 모듈로 나눈게 올바른 구조가 아닐 수 있다. 상황에 따라 다르다.
- 주문 관리가 주문 조회, 주문 취소만 있을 경우 모듈이 작으므로 고객 관리에 다시 통합하는게 합리적일 수 있다.
- 고객 관리가 지금보다 더 커질 경우 행동 방식을 다른 모듈로 추출할 수 있을지 검토해야 한다.
- 주문 관리의 작동에 필요한 고객 정보가 많은가? 그래서 모듈을 둘로 분리하면 시스템이 제대로 연동하기 위해서는 두 모듈의 결합도가 아주 높아야 하는가?
    - 래리 콘스탄틴의 인용문에 적혀있는 내용이다.

응집도를 결정하는 데 적합한 구조적 지표
- 응집 결여도(Lack of Cohesion)이라는 지표가 존재한다.

#### 3.3.2 결합도
코드 베이스의 결합도를 분석하는 더 나은 도구가 존재한다.
- 부분적으로 그래프 이론에 기반한다.

구심 결합도와 원심 결합도
- 구심 결합도: 해당 코드 요소(컴포넌트, 클래스, 함수 등)로 들어오는 연결의 개수를 측정
- 원심 결합도: 다른 코드 요소로 나가는 연결들의 개수를 측정

#### 3.3.3 핵심 지표들
추상도
- 추상적인 요소(추상 클래스, 인터페이스 등)와 구체적인 요소(구현 코드)의 비(ratio)

#### 3.3.4 주 시퀀스로부터의 거리
생략

#### 3.3.5 동변성
동변성(connascence)
- 구심 결합도, 원심 결합도 같은 결합에 대한 지표가 아니다.
- 아키텍트가 다양한 유형의 결합을 더욱 정확하게 설명하기 위한, 그리고 주어진 유형의 결합이 유발하는 전반적인 결과를 이해하기 위한 하나의 언어를 대표하는 용어

두 컴포넌트가 **동변적(connascent)**
- 한 컴포넌트가 변했을 때 시스템의 전체적인 정확성을 유지하려면 다른 컴포넌트도 변해야 한다는 뜻

동변성에는 정적 동변성과 동적 동변성이 존재

**정적 동변성(static connascence)**
- 소스 코드 수준의 결합을 의미한다.
- 주어진 대상이 어느 정도 결합하여 있는지를 나타낸다.

정적 동변성의 유형
- 이름 동변성
    - 여러 컴포넌트가 엔티티의 이름에 합의해야 한다.
- 타입 동변성
    - 여러 컴포넌트가 엔티티의 타입에 합의해야 한다.
- 의미 동변성
    - 여러 컴포넌트가 특정 값의 의미에 합의해야 한다. 규약 동변성이라고도 부른다.
    - 예시) int TRUE = 1; int FALSE = 0 같은 정의가 일상적인 언어들이 있는데, 누군가가 이 값들을 바꾸면 문제가 발생한다.
- 위치 동변성
    - 여러 컴포넌트가 값들의 순서에 합의해야 한다.
    - 예시) 메서드에 인자 순서를 다르게 넣으면 타입은 같더라도 의미가 달라진다.
- 알고리즘 동변성
    - 여러 컴포넌트가 특정 알고리즘에 합의해야 한다.
    - 예시) 클라이언트와 서버가 같은 보안 해싱 알고리즘을 사용해야 한다.

**동적 동변성(dynamic connascence)**
- 실행 시점에서의 호출들에 관한것

동적 동변성의 유형
- 실행 동변성
    - 여러 컴포넌트의 실행 순서가 중요하다.
    - 예시) 이메일 발송시 발신자, 수신자 속성을 설정한뒤 전송을 시도해야 한다. 순서가 어긋나면 제대로 실행되지 않는다.
- 타이밍 동변성
    - 여러 컴포넌트의 실행 타이밍이 중요하다.
    - 예시) 두 스레드의 실행 순서에 따라 공동 작업의 결과가 달라진다.
- 값 동변성
    - 여러 값이 서로 의존하며, 반드시 함께 변경되어야 한다.
    - 예시) 분산 시스템에서의 트랜잭션, 분리된 여러 개의 데이터베이스들을 사용하도록 설계된 시스템에서 어떤 하나의 값을 시스템 전체에 걸쳐 일관되게 갱신해야 하는 경우, 모든 데이터베이스의 해당 값을 전부 변경하거나 하나도 변경하지 않아야 한다.
- 신원 동변성
    - 여러 컴포넌트가 동일한 엔티티를 참조해야 한다.
    - 예시) 독립된 두 컴포넌트가 분산 대기열(Kafka, RabbitMQ) 같은 공통의 자료 구조를 공유하고 갱신하는 것

#### 동변성의 속성들
- 강도
    - 개발자가 시스템의 결합을 리팩터링하기가 얼마나 쉬운지를 나타낸다.
    - 동변성의 유형에 따라 동변성의 크기가 다르다.
    - 더 나은 유형의 동변성 쪽으로 코드베이스를 리팩터링하면 코드베이스의 결합 특성들을 개선할 수 있다.
        - 아키텍트는 동적 동변성보다 정적 동변성을 선호해야 한다.
- 지역성
    - 코드베이스에서 모듈들이 서로 얼마나 가까이 있는지를 측정한다.
    - 근접한 코드(같은 모듈 안의 코드)는 멀리 떨어진 코드(별도 모듈이나 코드베이스에 있는 코드)보다 동변성이 더 크고 다양하다.
        - 같은 유형의 동변성이라도 컴포넌트들이 멀리 떨어져 있을 때는 바람직하지 않은 결합을 나타내지만 컴포넌트들이 가까이 있을 때는 문제가 덜하다.
- 정도
    - 특정 모듈에서 클래스를 변경했을 때 그것이 시스템에 미치는 영향의 크기와 연관된다.
    - 변경에 영향을 받는 클래스가 많으면 동변성의 정도가 높다.
    - 동변성의 정도가 낮으면 다른 클래스와 모듈을 조금만 변경하면 된다. 따라서 코드베이스에 덜 해롭다.
        - 모듈의 수가 적다면 동적 동변성은 큰 문제가 되지 않는다. 코드베이스는 성장하는 경향이 있다. 코드베이스가 커짐에 따라 변경의 측면에서 작았던 문제가 훨씬 더 큰 문제로 변한다.

동변성을 이용해서 시스템 모듈성을 개선하기 위한 세 가지 가이드라인
- 시스템을 캡슐화된 요소들로 분해해서 전체적인 동변성을 최소화한다.
- 캡슐화의 경계에 걸쳐 있는 동변성을 찾아서 최소화한다.
- 캡슐화 경계 안의 동변성을 최대화한다.

짐 웨이리치가 제시한 규칙
- 정도의 규칙: 강한 유형의 동변성을 더 약한 유형의 동변성으로 변환하라.
- 지역성의 규칙: 소프트웨어 요소들 사이의 거리가 멀수록 더 약한 유형의 동변성을 적용하라.
